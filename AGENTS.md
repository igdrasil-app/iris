# iris, working agreement

iris is a macOS binary that gives coding agents (Claude Code, Cursor, Codex, OpenClaw) access to Apple apps, Calendar first. Swift, SwiftPM, macOS 14+, no dependencies unless they earn their place.

- This is the only instruction file. Do not add CLAUDE.md or similar; Claude Code and Codex both read AGENTS.md.
- One change per step, small enough to read as a single diff. Finish and verify a step before starting the next.
- No documents beyond README.md and this file. No tests unless a behaviour could break silently and running it by hand would not catch it.
- `make app` builds and signs `build/Iris.app`; the CLI is the binary inside it. Signing with the Developer ID is not optional: macOS binds permission grants to the bundle id and the signing identity.
- The binary must never depend on the current directory; agents run it from anywhere.
- CLI contract: JSON on stdout; errors on stderr, exit 1 at runtime and 64 for usage; dates in ISO 8601 with the Mac's offset. `--help` is the documentation agents read; keep it complete.
- `iris mcp` serves the calendar, notes and reminders commands as tools over stdio and writes nothing else to stdout. A tool is its command: a new option needs a row in the table in `Sources/iris/MCPTools.swift`.
- `iris mcp --http` offers the read tools named in `Sources/iris/MCPHTTP.swift` (the reminder reads only when the scope file names lists or says "all"; a file without `lists` offers none and never asks Reminders), the calendar writes only when the scope file says `"writes": true`, and the reminder writes only when it says `"reminderWrites": true` (which needs lists; `writes` never turns them on), on 127.0.0.1 only, behind a token read from a file (never an argument or the environment). Its stdout is one ready line; the request log goes to stderr and never holds arguments, results or the token.
- Over HTTP, unless its scope-file key is "all", every tool call carries the scope file's ids, pinned at start, as `--allowed-calendars`, `--allowed-folders` or `--allowed-lists`; the commands enforce them, and out of scope answers exactly like nonexistent.
- Over HTTP every write, calendar or reminder, passes the guards in `Sources/iris/MCPHTTPWrites.swift`, one guard for both kinds: one at a time, counted and saved before it runs in one shared hourly limit, never a series delete (delete_reminder always carries `--not-repeating`, pinned at start), recorded after. Any tool offered over HTTP that is not a read in `httpToolNames` is a write. The state folder is locked by one server and must be the user's alone; its files are mode 600 with no ACL.
- Over HTTP, unless the scope file says `"sharedEvents": true`, every update_event and delete_event carries `--only-mine`, pinned at start like the scope: an event with anyone else on it is refused, and so is `--span future` on a repeating event, after scope and existence and before any change.
- `iris remote status` is for the owner, never a tool (no row in `MCPTools.swift`): it reuses `readScopeFile`, `pinScope`, `readToken` and `httpOffering`, changes nothing, never prints the token or anything derived from it, and makes a lookup only where it cannot show a permission dialog. The menu bar shows the same `remoteState`, off the main thread and one check at a time, as an access word per app, never names.
- The menu bar's switch runs `iris mcp --http` through `RemoteServer` (`Sources/iris/RemoteServer.swift`, no AppKit): this binary, default paths, `--port` from defaults, stderr appended to `~/Library/Logs/iris-http.log`. It starts none while any other `iris mcp --http` runs, and never stops one it did not start; the one it recorded (pid and start time) that outlived its app, its parent now launchd, is stopped at the next launch. It creates a missing token or scope file (the scope sharing nothing), never replaces one.
- The menu's header shows who used the switch's server in the last 10 minutes and when, else when it was last used (`activityStatus` in `Sources/iris/Activity.swift`), with any warning winning; the icon shows a dot under the head, always drawn in the same place, until 3 seconds after the last request.
- A client's name is a label it gives itself: `activityLabel` sanitises it, only a server with `IRIS_REPORT_ACTIVITY=1` writes it, as an `@activity` line on stderr that `ActivitySplitter` keeps out of the log, and the menu app holds it in memory only, never logged or written to disk.
- Besides the switch's first-time file, only the menu writes the scope file (each app's Off, Read Only and Read & Write, its items, and Settings' events with other people): through `applying` and `writeScopeFile` in `Sources/iris/Scope.swift`, by id, whole and owner-only, and never over a file that cannot be read unless the owner chooses Reset, which keeps a copy; every file a tick writes keeps the parser's rules. What an app shared before Off is kept in `<scope file>.shared-before`, read and written only under the scope lock, saved before Off is written and cleared after an app shares again; `applying` takes and returns it and never reads it. A remembered selection may shrink to Off, never grow to all; only nothing remembered turns an app on with all, and a memory that cannot be read counts as nothing left. A tick that needs a listing, as the files are under the lock, is refused there and made again once listed; an empty listing is never a stand-in for none. The menu shows no port.
- A calendar name that matches nothing is an error, never a silent widening to every calendar.
- Writes change one event per call and print the result. A recurring event needs `--occurrence` or `--span future`; placeholder ids and read-only calendars are refused.
- Reminders can be read, added, changed, completed and deleted: `iris reminders lists`, `list`, `add`, `update`, `complete` and `delete` (tools `reminder_lists`, `reminders`, `add_reminder`, `update_reminder`, `complete_reminder` and `delete_reminder`; the writes over HTTP only with `"reminderWrites": true`). Every one takes `--allowed-lists`. EventKit reads an empty list of lists as every list: never pass one. A reminder is found only by `findReminder` (`calendarItem(withIdentifier:) as? EKReminder`), never `event(withIdentifier:)`, which crashes on a reminder's id. `add` sets no alarm: one written through EventKit is kept floating and fires at the wrong moment in another zone. `add --repeat` needs `--due` and builds its rule with `checkRepeat` and `recurrenceRule`, shared with `calendar add`, a new rule object per item; Reminders rewrites a monthly rule from the 29th to 31st (and yearly from 29 February) to the month's last day, and compares an end date with a date-only occurrence as the start of its day. `update` never touches alarms, so it refuses `--due` on a reminder with an alarm, and on one that repeats; a new due sets the start date as a first save does, and clearing it clears the start. `complete` changes only completion, saves only when that changes, and completes a repeating reminder only with `--occurrence` equal to its current due date: Reminders then moves it to its next occurrence and saves the occurrence done as a new completed reminder, found by comparing the list's completed reminders before and after the save.
- Iris sends nothing about the people who use it. On its own it makes two requests: Sparkle's update check to `SUFeedURL` (`updates.igdrasil.app`, which counts checks per day, version and country and keeps no address), with no system profile and no feed parameters; and `iris doctor`'s latest-release lookup on GitHub. A new request that leaves the Mac is the owner's decision, and README's "What Iris sends" changes with it.
- Notes are read only, through batched Apple Events: one event per property, never one per note. The only caller text ever put into a script is a note id that passed the id check.
- Plain, readable Swift over clever Swift. Comment only what the code does not already say.
